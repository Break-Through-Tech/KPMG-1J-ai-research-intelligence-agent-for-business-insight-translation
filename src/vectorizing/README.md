# Vectorization / Embedding Pipeline

## Overview

This directory contains the **vectorization stage** of the RAG (Retrieval-Augmented Generation) pipeline.

The purpose of this stage is to take the text chunks produced by the chunking pipeline and convert each chunk into a numerical embedding vector. These vectors represent the semantic meaning of the text and can later be stored in a vector database or vector index for semantic retrieval.

At a high level, the project pipeline now looks like:

```text
Raw Papers
    ↓
Preprocessing / Cleaning
    ↓
Chunking
    ↓
data/chunks.parquet
    ↓
Vectorization  ← THIS DIRECTORY
    ↓
Embedding Vectors + Chunk Metadata
    ↓
Vector Database / Indexing
    ↓
Query / Retrieval
    ↓
RAG Response
```

The vectorization code is intentionally separated from the vector database/indexing code. This stage is responsible for **creating embeddings**, while the next stage can decide how and where those embeddings should be indexed.

---

# 1. What This Component Does

The vectorization pipeline:

1. Reads the chunks generated by the chunking pipeline.
2. Validates that the chunk data contains the fields required for embedding.
3. Extracts the `text_for_embedding` field from every chunk.
4. Loads the embedding model.
5. Converts the text into dense numerical vectors.
6. Normalizes the vectors.
7. Verifies that valid embeddings were generated.
8. Saves the embeddings to a NumPy file.
9. Saves the corresponding chunk metadata to a Parquet file.
10. Generates a JSON report describing the vectorization run.

The default embedding model is:

```text
BAAI/bge-small-en-v1.5
```

This model generates a **384-dimensional vector** for each text input.

For example, if 500 chunks are embedded, the resulting embedding matrix has the shape:

```text
(500, 384)
```

If the full current dataset of 32,880 chunks is embedded, the expected shape is:

```text
(32880, 384)
```

The first number represents the number of chunks and the second represents the number of values used to represent each chunk.

---

# 2. Why Vectorization Is Needed

A normal keyword search mainly looks for matching words.

A RAG system needs to retrieve information based on **meaning**, not only exact wording.

For example, a user might ask:

```text
How can AI reduce repetitive work for companies?
```

A relevant research-paper chunk might instead contain:

```text
Artificial intelligence can automate routine business processes.
```

These sentences do not contain exactly the same words, but they express similar ideas.

An embedding model converts both pieces of text into vectors in the same numerical space. Semantically similar text should have vectors that are closer together.

This allows the retrieval stage to find relevant research even when the user's exact words do not appear in the paper.

# 4. Important Field: `text_for_embedding`

The vectorization pipeline embeds:

```text
text_for_embedding
```

rather than rebuilding the embedding text itself.

The chunking pipeline currently creates this field using the general structure:

```text
Title
Section: Section Name

Chunk text
```

For example:

```text
Retrieval Augmented Generation
Section: 1 Introduction

Retrieval augmented generation combines information retrieval with language models.
```

This is important because it provides additional context to the embedding model.

Instead of embedding only an isolated paragraph, the model also receives information about the paper title and the section where the text appeared.

The vectorization stage deliberately uses the chunking pipeline's `text_for_embedding` field directly. This keeps the boundary between the two components clear:

```text
Chunking decides what text should be embedded.
Vectorization converts that text into vectors.
```

If the chunking strategy changes later, the vectorization pipeline does not need to reconstruct those decisions.

# 6. `embedder.py`

## Purpose

`embedder.py` contains the code responsible for communicating with the embedding model.

The main class is:

```python
TextEmbedder
```

The default model is defined as:

```python
DEFAULT_MODEL = "BAAI/bge-small-en-v1.5"
```

Separating the model logic into its own class makes it easier to change the embedding model later without rewriting the rest of the pipeline.

---

## Model Initialization

When a `TextEmbedder` is created, the model is loaded with:

```python
self.model = SentenceTransformer(model_name)
```

The implementation uses the `sentence-transformers` Python package.

The constructor accepts:

```python
model_name
batch_size
```

The default batch size is:

```text
32
```

Instead of processing all chunks simultaneously, the embedding model processes groups of chunks.

For example:

```text
32 chunks
↓
Embedding model
↓
32 vectors
```

Then the next batch is processed.

This reduces memory requirements and allows large collections of chunks to be processed incrementally.

---

# 7. Document Embeddings

The method:

```python
embed_documents()
```

is responsible for converting chunk text into vectors.

It receives a list of strings:

```python
[
    "first chunk text",
    "second chunk text",
    "third chunk text"
]
```

and passes them to the SentenceTransformer model.

The important model call is conceptually:

```python
self.model.encode(
    texts,
    batch_size=self.batch_size,
    show_progress_bar=True,
    normalize_embeddings=True,
    convert_to_numpy=True
)
```

The result is a NumPy matrix.

For example:

```text
500 chunks
```

becomes:

```text
(500, 384)
```

This means there are 500 vectors and each vector contains 384 floating-point values.

The vectors are returned as:

```text
float32
```

to provide a standard numerical representation while avoiding the additional storage required by 64-bit floating-point values.

---

# 8. Normalized Embeddings

The pipeline generates normalized embeddings using:

```python
normalize_embeddings=True
```

This means each vector has approximately unit length:

```text
||embedding|| ≈ 1
```

During the real-data test, the pipeline reported:

```text
Mean vector norm: 1.0000
```

Normalization is useful for semantic retrieval because similarity can be compared efficiently using operations such as dot product or cosine similarity.

The pipeline also verifies the generated vectors before saving them.

---

# 9. Query Embeddings

`embedder.py` also contains:

```python
embed_query()
```

This method converts a user query into an embedding using the same model.

For example:

```python
embedding = embedder.embed_query(
    "How can RAG help businesses?"
)
```

The result is one 384-dimensional vector.

Using the same embedding model for documents and queries places both representations in a compatible vector space.

The retrieval stage can then compare:

```text
Query Vector
      ↓
Similarity Search
      ↓
Chunk Vectors
```

to identify relevant chunks.

The method also rejects empty queries rather than generating an embedding for an empty string.

# 11. Input Validation

Before performing the expensive embedding operation, the pipeline validates the input data.

The required columns are:

```text
chunk_id
paper_id
title
section
text
text_for_embedding
```

If one of these fields is missing, the pipeline raises an error.

This prevents a long embedding job from starting with malformed input.

The validation also checks for several additional problems.

### Empty dataset

The pipeline rejects an input file containing zero chunks.

### Missing chunk IDs

Every embedding needs to be traceable back to its original chunk.

Therefore, a missing `chunk_id` is treated as invalid input.

### Duplicate chunk IDs

Each chunk should have a unique identifier.

If duplicate IDs are detected, vectorization stops and reports the number of duplicates.

### Missing embedding text

Every row must contain `text_for_embedding`.

### Empty embedding text

A value containing only whitespace is also rejected.

These checks help ensure the vector database receives reliable data.

---

# 12. Embedding Validation

After generating the embeddings, the pipeline performs additional checks.

First, it verifies:

```text
number of embeddings == number of chunks
```

For example:

```text
500 chunks
500 embeddings
```

is valid.

But:

```text
500 chunks
499 embeddings
```

would raise an error.

The pipeline also checks that the vectors do not contain:

```text
NaN
Infinity
-Infinity
```

using NumPy's finite-value validation.

This prevents corrupted vectors from silently reaching the indexing stage.

The pipeline generates three files.

For the default model:

```text

```

```text

```

---

## 13.2 `chunk_metadata.parquet`

Location:

```text
data/vectorized/chunk_metadata.parquet
```

This contains the chunk information corresponding to the embedding rows.

The relationship is positional:

```text
embeddings[0]
```

corresponds to:

```text
chunk_metadata.iloc[0]
```

Similarly:

```text
embeddings[100]
```

corresponds to:

```text
chunk_metadata.iloc[100]
```

This relationship must be preserved by the downstream vector database/indexing stage.

The metadata makes it possible to take a retrieved vector and determine information such as:

```text
chunk_id
paper_id
paper title
authors
section
source text
arXiv URL
```

depending on which fields the retrieval implementation chooses to expose.

---

## 13.3 `embedding_report.json`

Location:

```text

```

This provides information about the vectorization run.

The report includes information such as:

embedding_dtype

This makes the run easier to inspect and reproduce.

# 17. Runtime Warning for CPU Users

Embedding thousands of chunks is computationally expensive.

The full current corpus contains:

```text
32,880 chunks
```

When tested locally on a CPU-only Windows environment, the complete run was projected to take multiple hours.

This does **not** indicate that the pipeline is stuck.

The progress bar may look similar to:

```text
15/1028 [01:54<2:26:01, 8.65s/it]
```

The value:

```text
2:26:01
```

is the estimated remaining runtime based on the current processing speed.

Runtime will depend heavily on:

- CPU
- GPU availability
- batch size
- available memory
- model
- chunk length
- total number of chunks

For development, it is much faster to validate the pipeline on a representative subset before running the entire corpus.

# 24. Windows Encoding Changes Needed During Integration Testing

While generating the real chunking output on Windows, two encoding issues were encountered.

These were related to preparing/running the upstream chunking pipeline on Windows and were **not failures in the vectorization model itself**.

They are documented here because another teammate using Windows may encounter the same problems.

---

## Issue 1: PowerShell File Encoding

The preparation script was initially obtained using PowerShell output redirection.

This resulted in Python reporting an encoding-related syntax error.

The script was recreated explicitly using UTF-8:

```powershell
Remove-Item prepare_for_chunking.py
git show origin/abdullah-eda:notebooks/prepare_for_chunking.py | Out-File -Encoding utf8 prepare_for_chunking.py
```

This ensured Python could correctly read the script.

---

## Issue 2: Writing Unicode JSONL

The preparation script initially opened its output file without explicitly specifying UTF-8.

On the Windows environment used for integration testing, Python attempted to use the Windows `cp1252` encoding.

This caused a `UnicodeEncodeError` for characters that could not be represented using that encoding.

The local preparation script was changed from:

```python
with open(a.dst, "a" if a.append else "w") as f:
```

to:

```python
with open(
    a.dst,
    "a" if a.append else "w",
    encoding="utf-8"
) as f:
```

After this change, generation succeeded:

```text
1,217 new papers
19,613 sections
3 skipped as unusable/empty
```

---

## Issue 3: Reading Unicode JSONL During Chunking

The chunking pipeline then encountered:

```text
UnicodeDecodeError
```

because the generated JSONL file was UTF-8, while the Windows environment attempted to read it using `cp1252`.

For local integration testing, the file read was changed from:

```python
with open(path) as f:
```

to:

```python
with open(path, encoding="utf-8") as f:
```

After reading the JSONL explicitly as UTF-8, chunking completed successfully:

```text
chunking 19,613 sections from 1,217 papers
wrote 32,880 chunks to data/chunks.parquet
```

These upstream modifications were used to generate the local test data. The vectorization contribution itself remains isolated under `src/vectorizing/`.

# 28. Handoff to the Vector Database / Indexing Stage

The next stage should primarily consume:

```text
data/vectorized/embeddings.npy
```

and:

```text
data/vectorized/chunk_metadata.parquet
```

Load them with:

```python
import numpy as np
import pandas as pd

embeddings = np.load(
    "data/vectorized/embeddings.npy"
)

metadata = pd.read_parquet(
    "data/vectorized/chunk_metadata.parquet"
)
```

The downstream implementation should preserve the positional relationship:

```python
embeddings[i]
```

corresponds to:

```python
metadata.iloc[i]
```

For example:

```python
vector = embeddings[25]
chunk = metadata.iloc[25]

print(chunk["chunk_id"])
print(chunk["title"])
print(chunk["section"])
print(chunk["text"])
```

The vector database implementation can then associate each vector with its `chunk_id` and whichever metadata fields are useful for retrieval.

# 29. Important Design Boundary

This component does **not** decide:

- which vector database should be used,
- how the index should be configured,
- how many chunks should be returned for a query,
- which reranking strategy should be used,
- how retrieved chunks should be inserted into an LLM prompt.

Those responsibilities belong to later RAG stages.

This component is specifically responsible for:

```text
Chunk Text
    ↓
Embedding Model
    ↓
Validated Vector Representation
```

Keeping these responsibilities separate makes it easier to test or replace individual RAG components.
